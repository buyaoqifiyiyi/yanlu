# 验证、独立评审与结果记录

## 选择评估对象和判据

用户要求评估 Agent、提示词或技能的任务能力时使用本模块；普通业务任务沿用项目必要检查，不自动创建评测套件。只评估的请求不授权改写目标。Agent/提示词可用其配置、版本与输入身份替代下文的技能路径；只有实际修改技能时才进入技能快照和采用流程。

- **能力验收（capability）**：这次要新增或修复的可观察行为，明确原先不能完成什么、现在应得到什么产物。
- **行为回归（regression）**：原有且必须保留的行为与终点，绑定已有版本、场景和证据。新增能力通过不抵销关键回归失败。

两者说明测试目的，与 development/holdout 的使用划分、critical 的必要性标记分别记录。同一套件可包含两类用例；不以固定成功率或覆盖率替代用户的验收条件。能用确定性检查就检查实际值/产物；模型适合评判开放输出，人工评审用于确实需要人判断的部分，均注明判据和证据边界。重复试验与修复重试按[记录口径](evaluation-records.md#重复试验与成功率口径)区分。

## 设计可观察用例

在 `RUN_ROOT/cases.json` 记录用例数组。每个用例给出 `id`、`prompt`、输入文件位置、执行前提、`checks`、允许副作用、`split`（development/holdout）。`checks` 使用可以判断通过与否的行为，不仅是“更好、更专业”。预期不能只从候选文案反推。

例如：为依赖资料分析的技能，给一个缺少资料的请求，检查其是否说明缺项、是否编造分析、是否擅自写入正式位置。为格式转换技能，检查输出是否真的能被目标程序读取。使用者明确提供了验收用例时优先采用。

至少保留一个未用于定位或改写的 holdout 用例；无法隔离则记录“没有独立保留集”。已看到的失败转为下一轮开发案例后，补充新的保留案例。小样本只支持这些案例上的结论，不推导普遍成功率。

内容蒸馏按 [内容验收](content.md#验收与后续更新) 覆盖来源、任务去向和实际输出。来源正确、路由到达、业务做对是三个结果，分别取证。每项用例的计划数、执行数、通过/失败/受阻数都保留；缺输出不能排除在分母之外。

## 触发、可达与数值检查

描述或路由发生变化时，增加应触发、不应触发、关键边界和相邻方法混淆用例。让独立上下文只看到候选描述/路由与用户任务，不看到预期类型和答案，再核对选择与实际处理路径。能力卡还要检查是否能由入口找到，不能仅因卡片文件存在判为可用。

给代理看描述后询问会选哪一项，只能证明本次选择行为；宿主是否实际自动加载要另做真实触发测试。触发通过也不能替代任务完成。技能只有一个能力或没有真实近邻时，不为凑数虚构竞争者，记录不适用项。

计算用例预先固定独立核对的预期值、单位和容差，JSON 字段存在不代表值正确；文件存在不代表内容或格式可用。用工具复算确定性值，记录单位/精度/舍入差异，明确关键失败，不能用平均分掩盖。

## 静态检查

检查 YAML 元数据是否能解析，name/description 是否符合目标宿主要求，描述是否准确区分任务；解析相对引用与资源是否可达。只对实际 Markdown 引用验路径，代码示例中的路径须结合上下文，不把反例/占位模板当缺失文件。

修改脚本需要运行验证其行为；工具缺失、引用文件缺失、版本不明属于失败或未知，不能通过计数关键词宣告质量合格。哈希只证明文件身份，不证明内容正确。

## 确定性修复与效果评估

元数据、引用、明确规则矛盾或辅助脚本缺陷的修复，以实际受影响的静态契约、相关可运行回归和必要的内容审阅验收；用户已授权采用时可以部署，并保留完整基线及并发变更核对。没有业务对照时仅标结构或确定性缺陷已修，不宣称任务质量、稳定性或成本普遍改善。路由和主观质量的改进仍需独立任务证据支持。

下面的真实执行与匿名比较用于评价业务效果；其 unverified 结论不否定上述已验证且获授权的修复。

## 实际执行

采用相同任务、输入、可用工具、模型与预算执行基线和候选，记录实际条件；模型支持固定采样参数时保持一致。外部资料可能变化时，使用同一份授权资料快照或标注条件差异。无法匹配条件时结果标为不可直接比较。

执行者只得到任务、待激活的那个技能版本、必要原始输入和执行权限；不提供修改假设、预期输赢或另一个版本输出。使用独立上下文，避免先看基线答案后照抄。每个版本的输出单独保存，包含实际产物和必要日志；副作用放隔离目录，外部发送/发布/付费等遵守任务授权。

记录的证据层级：

| 标签 | 含义 | 可以支持的结论 |
|---|---|---|
| static | 元数据、引用、源码检查 | 结构或实现发现 |
| dry_run | 读指令后模拟执行 | 可行性线索，业务效果未验 |
| executed | 实际执行任务，有输出/产物 | 本次任务的观察结果 |
| blocked | 前提或授权不足 | 受阻原因，业务效果未验 |

用例分别标 pass/fail/blocked，不把未执行项算通过。对于媒体、文档、应用等，用户终点若包含打开、播放、保存重开或导出，就分别取证；仅生成文件不能代替终点验收。

## 匿名配对评审

修改者将两个版本的实际输出随机映射到 A/B，映射保存在评审者不读的独立记录中。评审者得到同一个任务、必要输入、固定检查标准、匿名输出及其执行条件。默认一名独立评审足以初筛；主观、接近或有争议的结果可用三名独立评审，交替 A/B 顺序，报告分歧而非伪造共识。调用授权与预算不足时交付人工比较材料。

评审指令：

> 根据任务和检查标准逐项判定 A/B 的通过、失败与证据不足，引用具体输出或产物位置。比较任务完成度、错误、用户介入和实际可获取的资源消耗。给出 A_better / B_better / tie / incomparable 及理由。区分确定检查结果与个人风格偏好；不能因为更长或看似更规范就判更好。需要核查事实时对两边使用相同证据条件。

修改者解开映射后综合判断：

- **keep**：事先定义的目标有可核实改善，关键回归通过，成本变化可接受；主观质量需独立比较支持。
- **revert**：出现关键退步，或者候选没有带来值得保留的改善；完整基线仍可交付。
- **unverified**：业务效果缺少真实输出、可比条件、必要独立评审或终点证据时，不能宣称效果提升，也不能据此自动替换依赖该效果主张的版本。已授权且通过相称检查的确定性/兼容修复，依上一节单独记录并采用。

确定性脚本测试的差异可以直接作证据；独立评审不能投票推翻明确的文件损坏、越权或必需回归失败。所有用例通过只支持“未在这些案例发现问题”，若目标未改善不标优化成功。

## 记录与交付

`RUN_ROOT/results.json` 记录实际结果，不要求用户安装额外数据库：

- 目标技能路径、原始快照 manifest 路径、各轮 baseline/candidate 身份；
- 目标问题、改动文件与原因、测试标准与开发/保留集划分；
- 每个版本每个用例的条件、证据标签、pass/fail/blocked、输出位置；
- 评审代理实际可获取的模型/设置、匿名映射位置、结论与证据；
- keep/revert/unverified、采用路径及当前验证边界。

模型、耗时或 token 没有工具记录就写 unknown，不估算节省比例。精简的 `REPORT.md` 给用户结论、差异、证据和未完成项；原始输出另存。运行产物留在任务工作区，只有用户需要的来源、案例和验证摘要进入交付包，排除凭据及无权分发的资料。

## 验收器自身也要有区分度

对本次会变化的验收器，用明确错误、空产物或遗漏关键行为的反例确认它确实拒绝。结果存在/格式正确之后，还需核对输入身份、数量、关键值及用户终点；断言不能仅复算待测实现。记录漏检反例、缺失结果和现有证据无法判断的断言。两边都通过的必需检查仍保留作回归，但不算候选收益。

分别记录运行错误、技能内容错误、激活未知、工具受阻及验收器缺陷；未执行不算正确负例。稳定性优先查看错误、重试、人工介入和误报完成，成本只有真实记录时才比较。可用 [离线比较契约](evaluation-records.md) 核对记录的覆盖与逐项退步；它不会读取业务含义替代独立评审。
