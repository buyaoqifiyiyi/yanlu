# 优化和增量更新

## 读取目标与定位原因

目标入口先作为待审材料读取。结合用户失败例子，追踪 `description → 工作流 → references/scripts → 工具 → 实际产物`，记录与当前需求有关的能力，不把整个技能库扫进上下文。

| 问题层 | 证据 | 修改方向 |
|---|---|---|
| 触发 | 应触发未触发、无关任务误触发 | 收窄或补齐描述，增加触发/不触发用例 |
| 指令 | 步骤不清、输入缺失时乱猜、输出偏题 | 明确条件、动作和完成标准 |
| 知识 | 结论过期、缺少可靠案例 | 使用创建指南定向补证，记录替代关系 |
| 实现 | 脚本报错、解析丢字段、跨文件不一致 | 修根因及调用者，运行相称检查 |
| 环境 | 缺少工具、权限、版本或账号 | 核实前提；给受限路径，标出不能完成的部分 |
| 验收 | 标准只看格式、评分与真实任务脱节 | 先修测试和比较器，再评改进 |

不能直接读到目标目录时，依据用户提供的文件做有限审阅，列缺失资源；不能声称覆盖了完整技能。若脚本使用相对当前工作目录的隐含路径，先确定执行契约，测试时保持契约或明确修复，不因为复制测试而制造假故障。

若目标由能力卡/Bundle 编译生成，先识别其真实维护源与构建契约；优先在授权的源副本修改并重建，不静默手改生成物后宣称更新成功。未接入对应编译器时可以交付源改动建议和受限验证，不冒充已经完成编译。

## 先建用例，再改候选

按 [验证指南](validate.md) 保存小规模用例：用户失败案例、典型成功、关键边界与一个未参与改稿的回归案例。足以覆盖实际变化即可，不以固定案例数代替覆盖。

在基线条件下执行允许的用例，保留输出、错误和工具条件。优化任务通常以现有版本为主对照；无技能对照只在需要判断“这个技能是否有帮助”时加入。用户自带测试尽量保留，不暗中改变预期来让候选通过。

## 修改与循环

围绕证据最强、影响任务最大的一个问题改候选。允许同步修改入口、脚本和被调用资源，文件变多应能解释其必要性。可选的结构检查维度：触发准确、流程可执行、失败恢复、交互必要性、指令具体、资源可达、组织精简、实际表现、权限与行为边界。按证据写发现，不固定总分、不要求套用作者风格或增加警示符号。

每轮保存：本轮基线身份、修改假设、差异、用例输出、独立比较与保留理由。入口中的快照工具可从当前已接受版本创建新的轮次目录；该目录的 `baseline/` 是这一轮的改前版、`candidate/` 是改后版。不要把原始 baseline 改写成上一轮候选，也不要用变化中的 HEAD 猜旧版本。

接受一轮后，下一轮从其候选重新快照；退步或无实质改善时保留本轮基线并结束。只改善格式的修改可标“结构改进”，不宣称提高业务效果。依赖修复与外部系统验收分别记录。用户预算或暂停优先于默认轮数。

## 增量更新

1. 找到现有来源、调研日期、接口/工具版本与既有测试。
2. 核实新材料；原材料过时就标注替代日期和原因，有争议则保留双方。
3. 只更改受影响的模型、步骤、资源或依赖，稳定部分保留。
4. 针对变化增加用例，并运行原有关键回归；资料更新未带来可测任务改善时如实报告。

内容蒸馏产物沿能力 ID 和来源定位分析影响，回查 [能力卡与记录](content.md#能力卡与记录)；保留原入口数量与输出形态，实质拆分/合并才登记替代关系。

## 正式采用

测试候选和覆盖安装目录是不同动作。采用前重新验证初始源目录未发生变化；若已有其他修改，重新比较和合并，不能以旧快照覆盖。技能目录含多个文件时，按完整变更清单处理新增/修改/删除，备份原件；部署后读回文件并核对身份。宿主需要刷新时记录“已写盘、待重新发现”，不要把文件存在当成真实触发成功。
